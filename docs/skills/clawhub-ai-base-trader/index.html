This skill presents CRITICAL and HIGH severity security risks. The primary concerns are: (1) hardcoded credential paths creating exposure risk, (2) complete dependency on an unverified external trading tool (bankr) enabling tool poisoning, (3) command injection vulnerabilities in parameter handling, (4) lack of enforcement for stated safety limits allowing unbounded automated trading, and (5) deceptive framing of high-risk gambling as systematic trading. The skill handles financial transactions and credentials but lacks fundamental security controls like input validation, credential protection, and circuit breakers. The automated trading features could lead to significant financial loss if exploited or if the external bankr tool is compromised. The 'launch sniping' functionality promotes extremely high-risk behavior (80% expected loss rate) with inadequate warnings. Immediate remediation is required before this skill should be used in any production environment.

The skill hardcodes the path to Bankr API credentials at ~/.clawdbot/skills/bankr/config.json and references this configuration file multiple times. This creates a risk of credential exposure if the skill or its logs are shared, and establishes a predictable target for credential theft.

HIGH External Tool Dependency Without Verification Unauthorized Tool Usellm

The skill depends entirely on an external 'bankr' tool located at ~/clawd/skills/bankr/scripts/bankr.sh with no verification of its integrity, authenticity, or behavior. All trading commands are passed directly to this external script, creating a tool poisoning risk where a compromised or malicious bankr tool could execute arbitrary actions.

Remediation: Implement cryptographic verification of the bankr tool (signature checking, hash validation). Add version pinning and integrity checks. Provide clear warnings about the external dependency and its security implications. Consider sandboxing or limiting the bankr tool's capabilities.
HIGH Command Injection via Unvalidated Trade Parameters Command Injectionllm

The log-trade.sh script accepts user-controlled parameters ($1-$6) and uses them directly in shell commands and JSON construction without validation or sanitization. Parameters like TOKEN, REASON, and TX could contain shell metacharacters or JSON injection payloads.

scripts/log-trade.sh

ACTION=$1
TOKEN=$2
AMOUNT_USD=$3
PRICE=$4
REASON=$5
TX=$6
Remediation: Implement strict input validation for all parameters. Use proper JSON escaping (jq --arg for safe variable interpolation). Validate that ACTION is one of allowed values (BUY/SELL). Sanitize TOKEN names against a whitelist pattern. Validate numeric inputs (AMOUNT_USD, PRICE).
HIGH Unbounded Automated Trading Without Circuit Breakers Resource Abusellm

The skill promotes automated trading strategies (DCA, limit orders, stop losses) but lacks implementation of the stated safety limits. The instructions mention 'MAX_DAILY_LOSS = -20%' and 'STOP TRADING FOR 24 HOURS' but provide no mechanism to enforce these limits, allowing unbounded automated execution that could drain funds.

SKILL.md

The framing uses professional trading terminology to legitimize what is effectively gambling with extremely poor odds, potentially misleading users about the true risk.

MEDIUM Sensitive Financial Data Logging Without Protection Data Exfiltrationllm

The skill logs all trades including amounts, tokens, reasons, and transaction hashes to data/trades.json without encryption or access controls. This creates a persistent record of financial activity that could be exposed through file system access, backups, or skill sharing.

Remediation: Encrypt the trades.json file at rest. Implement access controls to restrict file permissions (chmod 600). Add options to disable logging or use ephemeral storage. Warn users that trade history is stored locally. Consider hashing or redacting sensitive fields.
MEDIUM Unsafe JSON Manipulation with jq Command Injectionllm

The log-trade.sh script uses jq to append trades to a JSON file, but constructs the JSON object using shell variable interpolation without proper escaping. While jq is used for the append operation, the initial JSON construction is vulnerable to injection if parameters contain special characters.

scripts/log-trade.sh

TRADE=$(cat <<EOF
{
  "timestamp": "$TIMESTAMP",
  "action": "$ACTION",
  "token": "$TOKEN",
  "amount_usd": $AMOUNT_USD,
  "price": $PRICE,
  "reason": "$REASON",
  "tx": "$TX"
}
EOF
)
Remediation: Use jq's --arg flag for safe variable interpolation: jq --arg action "$ACTION" --arg token "$TOKEN" --argjson amount "$AMOUNT_USD" '. += [{action: $action, token: $token, amount_usd: $amount, ...}]'. This ensures proper JSON escaping and prevents injection.
